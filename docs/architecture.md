# Architecture

How Atlas works today, one section per area. The reasons behind each part are in `docs/decisions/` (the ADR numbers below). Read this file before changing how a part works, and update it in the same commit when you do. Each app's `CLAUDE.md` holds its own language, style and local rules.

## Request flow and source adapters

The web app submits a URL to `POST /api/jobs`; the URL is a video (YouTube only; other video sites are refused with "Only YouTube videos are supported") or an article, detected from the host and overridable. The server queues a job and its worker runs it in the background, one at a time, through a source adapter that turns the job into one source document (ADR 0030).

## Transcription

For a video, the YouTube Data API gives the title, channel and length (`YOUTUBE_API_KEY`), then the Gemini Developer API (`GEMINI_MODEL`, `GEMINI_API_KEY` as a header, plain `fetch`; Vertex AI refused YouTube input from the VM's service account) is given the public YouTube link and writes the transcript in one request, so nothing is downloaded and the VM never contacts YouTube for the video (ADRs 0081–0083); if Gemini stops at its output limit the partial transcript is kept and marked truncated; the transcript is stored as metadata plus plain text, with no timestamps (ADR 0074), and formatters render it as Markdown (default) or TXT.

## Articles, feeds and Gmail

Ingested text (a transcript, an article, a note, the notes' titles and openings) goes into every Claude prompt inside a `<source_content>` block, and a learner's typed answer inside `<learner_answer>`; the locked instructions say the block is material to work on and never instructions, and a closing tag inside the text is neutralised (v1.1.1). Every page, feed and feed-discovery fetch resolves the host first and refuses loopback, link-local, private-network and unique-local addresses, again after each redirect (ADR 0096); the e2e stack and the unit tests switch this off with `FETCH_ALLOW_PRIVATE`, which the server refuses outside `NODE_ENV=test`. For an article, the server fetches the page itself, extracts the main text with Readability and stores it as Markdown (ADR 0031); a page it can't read is handled by pasting the article's text, which skips the fetch. Gmail (ADR 0035): Naresh connects his account once in Settings (read-only OAuth run by the server, the refresh token stored encrypted with a key from `.env`), adds sources that match emails by Gmail labels or a search, and the same poller reads new matching emails; each waits in the same inbox, and summarizing one converts the email's whole body to Markdown (ADRs 0036, 0040) and queues an article job whose note links back to the email, so nothing downstream knows it came from Gmail (one inbox for feed items and emails, ADR 0038; job-alert intake is deferred, ADR 0041). Feeds (ADR 0032): Naresh subscribes to RSS or Atom feeds in Settings, a poller in the server process checks them on a schedule, and new items wait in the inbox on the home page; nothing is fetched or summarized until he summarizes an item (or switches a feed to summarize automatically), which turns it into a normal job.

## Summaries and prompt profiles

The worker then sends the transcript or article to Claude for a summary (title, key points, quotes, tags; article notes have no timestamps). What the summary focuses on comes from a prompt profile, a named, versioned and editable guidance text that Naresh manages in Settings (the locked instructions that keep the output shape are always sent with it), and the model is chosen in Settings and can be overridden per video; both can be changed and the summary regenerated from the review screen. Every summary attempt is recorded with its model, prompt version, tokens and estimated cost.

## Linking and the agent

Linking (ADRs 0042–0046): when a summary completes and `AGENT_SECRET` is set, the job enters a `linking` status and the worker calls the vault agent service (`apps/agent`, reached at `AGENT_URL` with a bearer secret) with the note; the agent runs a Claude tool-use loop over read-only vault tools and returns link suggestions (existing notes, existing concepts or new concepts, each with an anchor phrase or a place under `## Related`), which the server stores per job with its own run record (model, linker prompt version, tool calls, tokens, cost). Linking never fails a job: on any error the job goes to review with a link error and can be retried. The linker prompt is a second, editable profile in Settings, with locked instructions served by the agent.

Where a Claude call lives (ADR 0103): if Express can assemble the whole input up front and the model answers in one structured reply, the call is a single Claude call in Express; if the model must decide what to read (list, search, open, follow) before it can answer, it is an agent in the agent service. The test is the input, not the importance of the feature: a cap such as "first N characters of M notes" means Express is guessing, and the call is an agent. Read-only isolation and Python-shaped data work can move a borderline call into the service but never move a real agent out of it. Express stays the orchestrator (run rows, usage, post-checks, every write); an agent reads and returns.

| Call | Where | Why |
| --- | --- | --- |
| Summarize | Express | One source in, one reply out |
| Melete questions, grading, map, suggest resources | Express | One note or one concept in, one reply out |
| Wikilink suggestions | Agent service | Must search the vault |
| Melete syllabus draft | Agent service, `POST /v1/syllabus` (ADR 0105) | Decides which notes to read |

Every agent shares one runner (ADR 0105): `atlas_agent/runner.py` takes an `AgentSpec` (system text, first message, model, tools, the submit tool and its Pydantic model, and `Limits` for turns, tool calls, output tokens and timeout) and returns an `AgentRun`, either `SUBMITTED` with the validated submission or `FAILED` with a reason, plus usage. It owns the loop: the limits and the timeout, one nudge and then failure when Claude replies without a tool, one retry after an invalid submission, and prompt caching (the system text, the last tool and a breakpoint that moves to the newest user message each turn, so earlier turns are billed as cache reads). An endpoint adds only its instructions, first message, tools, submit model and post-checks; the linker's `linker/loop.py` is exactly that. The vault tools (`list_notes`, `search_vault`, `read_note`, `list_link_targets`) come from `vault_tools( root, settings, include )` in `vault/toolset.py`, built against whatever root they are given, with every path still checked by `vault/paths.py`.

The agent's contract is Pydantic first and its Zod mirror is generated (ADR 0104): `uv run python -m atlas_agent.contract.export` writes `apps/agent/schema/*_contract.json`, and `pnpm --filter @atlas/shared generate:agent` turns it into `packages/shared/src/agent.generated.ts` (`agent.ts` re-exports it). Cross-field rules live in Pydantic as discriminated unions, so the JSON Schema carries them: the link response is a union on `outcome`. The generator supports only the keywords the contract uses and fails on any other. The gate's contract step regenerates both files and fails if either changed.

## Review and save

In review Naresh accepts or rejects each suggestion; accepting inserts the `[[wikilink]]` into the stored draft in one transaction with the decision, so the vault is still written only by the save. The note is stored as one Markdown string, front-matter included. Naresh reviews and edits it in the web app, which autosaves it to the server as a draft (each save restarts the 24-hour expiry), and chooses a vault folder for it; saving writes the stored draft into that folder of the Obsidian vault (a mounted folder, all writes confined to it) and deletes the transcript. Jobs are stored in SQLite, and unreviewed ones expire after 24 hours without an edit. The web app polls the job's status and offers the downloads.

## Lifecycle, logs and Status

Lifecycle (ADR 0048): every job status and allowed move is defined once in `apps/server/src/jobs/lifecycle.ts`; `moveTo` enforces it, sets expiry from the target state and logs a refused move, and the repository's status lists come from it. Logs (ADR 0049): the server (pino) and the agent write one JSON object per line, a job's ID is on every line about it and travels to the agent as `X-Job-Id`, and no secrets or note text are logged. Status (ADR 0050): every check of a feed, Gmail source, the Gmail connection, the agent, the transcription model, replication (when `LITESTREAM_METRICS_URL` is set), and each user's vault sync (when `VAULT_SYNC_STATUS_DIR` is set) goes through one `recordCheck` into `health_status` (the last 5 errors in `health_errors`); `GET /api/status` feeds the Status panel on the Settings → Sources tab and the warning badge on the drawer's Settings item.

Two checks read a file or a metrics page rather than call a service. Replication (ADR 0076) reads Litestream's Prometheus text with a 2-second timeout; it fails when the page can't be read or `litestream_sync_error_count` rose since the previous check (the first sample never fails, a counter that went down means a restart), and its detail is the time the check saw `litestream_sync_count` rise, because Litestream exposes no last-sync metric; an old last sync alone is never a failure. Vault sync (ADR 0075) reads `<VAULT_SYNC_STATUS_DIR>/<vault folder>.json`, written by that user's sync container (`VaultSyncStatusFile` in `packages/shared/src/status.ts`: `state` of `starting`, `running` or `failed`, `since`, `heartbeat_at`, `last_error`, `cli_version`), for every active user with a vault, and records a `vault_sync` check whose subject is the vault folder. It fails when the file is missing or doesn't parse, when `state` is `failed` (the message is `last_error`), or when `heartbeat_at` is more than 5 minutes old. A member's Status panel shows their own row; the admin sees every active user's row, named `Vault sync: <name>`, and may read any of their error histories (a member's request for another folder is a 404). At start `pruneHealth()` deletes the health rows of checks that are not configured, so a removed `LITESTREAM_METRICS_URL` or `VAULT_SYNC_STATUS_DIR` leaves no stale row.

## Backups and replication

Backups (ADR 0076, which supersedes 0051): the manual button is gone; on the VM Litestream replicates the database to a bucket, and the server only sets `busy_timeout = 5000`, writes its pre-migration and pre-0.9 set-aside copies to `pre-migration/` next to the database, and refuses to start on a database from a newer version.

## Settings

Settings (ADR 0052) is routed tabs, Prompts / Models / Sources, under a data router with one unsaved-changes guard.

## Melete

Melete (ADRs 0054–0060) is a second module of the same server, web app and database: the user picks a learning root in the vault, each folder in it is a subject, and a scan (on demand, 30-second rule, no watcher) tracks notes by path and a body hash so moves keep their history (ADR 0057); a folder or note it can't read is skipped, its notes are left exactly as they were, and the Melete page lists the skipped paths until a later scan reads them. The folder picker skips an unreadable folder the same way and logs it. Enrolled notes are queued in `melete_notes` and a generator loop beside the worker asks Claude for recall questions in one call from Express, not the agent (ADRs 0055, 0058); questions are scheduled with FSRS through `ts-fsrs` at 90% target recall (ADR 0056). In review, typed answers are graded by a second Claude call that suggests a rating, or the user rates in quick mode; the rating updates the card and writes a review row in one transaction. **Melete never writes to the vault** (the one exception is the empty learning-root folder a user creates from Settings, made on save, ADR 0072); it reads it and keeps all its data in the `melete_*` tables, and its two prompts are profiles in Settings with a `purpose`. The seeded Study summary profile and folder memory (the picker starts on the last folder used with the job's profile, `Job.default_folder`) are ADR 0059.

Order of work in the Melete generator (ADRs 0058, 0089): on start it puts notes left `generating` or `mapping` by a restart back in the queue (a subject left `drafting` needs no recovery, because `drafting` is the queue). Each pass then repeats one step at a time, always starting again from the top: draft the syllabus of a subject that is `drafting` (each subject once per pass, as it stays `drafting` until its draft finishes), else generate questions for a queued note, else map a note queued for it (`claimNextMapping`, only when its questions are not waiting). Every claim takes the same turns between users as the job worker, and the pass ends when nothing is left; a failure inside a step is stored on the note or subject, and an error outside one is logged and ends the pass.

Concept layer (v1.1, ADRs 0089, 0094): schema 15 gives a subject a target level, an intent and a syllabus status, and adds sections, concepts, note-to-concept mappings and a concept label on each question. Since 1.2 the syllabus is drafted by the agent service (ADR 0105): Express sends the vault, the subject's folder, name, target level, intent, model and the prompt's guidance to `POST /v1/syllabus` (`draftSyllabusWithAgent`, waiting up to `AGENT_SYLLABUS_TIMEOUT_MS`), and the agent runs a tool loop over that folder only (`list_notes`, `search_vault`, `read_note`, then `submit_syllabus`); `melete/syllabus.ts` trims what comes back to at most 80 unique concepts. `POST /api/melete/subjects/:id/syllabus/draft` only sets the subject `drafting`, and the Melete generator loop, which takes drafts before question generation, makes the call and stores it as `draft` or `failed` (the old syllabus is kept on a failure, an agent that cannot be reached fails the draft with "Agent service unavailable", there is no fallback, and a subject left `drafting` by a restart is simply taken again). Each attempt is a `syllabus` row in `melete_runs`, with its tokens, cost, turns and tool calls (schema 18). Settings shows the syllabus's locked instructions from the agent, as it does the linker's. The draft is edited as a whole: `PUT .../syllabus` is diffed against the stored one by id (`melete/syllabusDiff.ts`), so a renamed or moved concept keeps its mappings and question labels and only a removed one loses them; `POST .../syllabus/approve` sets `approved` and queues every enrolled note for mapping. For an approved syllabus, question generation is one call that also maps the note (`generateApprovedQuestions`): Claude sees the concepts as short refs (`c1`…, `melete/conceptRefs.ts`) and answers with the note's concepts (at most 5), an off-syllabus suggestion when none fits, and a concept ref on each question; the server maps refs back to ids, gives a question outside the note's concepts the first one, stores the mapping as `claude` (hand pins are cleared, since the content changed) and flags an unmapped note `off_syllabus`. An unapproved subject keeps the plain call. Syllabus-driven remaps use a separate **Map** call (`mapNote`, `melete/map.ts`, `services/meleteMapping.service.ts`): a note is queued with `mapping = 'queued'`, the Melete loop takes it third (after drafts and generation, and only once its questions are not waiting) and claims it with `claimNextMapping`, which takes the same turns between users. Map rewrites the note's mapping and its questions' concept labels and nothing else, so no card, state or question changes; a hand-mapped (pinned) note keeps its concepts and is only labelled (a pin with no concepts left, after a redraft, is mapped in full and unpinned). A failure sets `mapping = 'failed'` with the reason, keeps the old mapping and is retried with `POST /api/melete/notes/:id/retry`; notes left `mapping` by a restart are requeued at start. Remaps are queued, never run inside a request: approving queues every enrolled note; a save of an approved syllabus queues the unpinned `flagged` notes when a concept was added and the unpinned notes left with no concept when one was removed (a rename, a new description or a move queues nothing); `POST .../syllabus/remap` queues every enrolled, unpinned note. A note Map is working on now is never queued again. A hand edit (`PUT /api/melete/notes/:id/concepts`) writes the mapping as `hand`, pins the note, clears its off-syllabus flag and queues a labels-only Map; `POST /api/melete/notes/:id/off-syllabus` either dismisses the flag or adds the suggested concept to a chosen section and maps the note to it by hand (and queues the other flagged notes, since a concept was added). The Notes tab shows each note's concepts, its mapping state and the flag; the note page has the mapping editor. Coverage and mastery (ADR 0090) are computed on every read, never stored: `melete/mastery.ts` (pure) scores each active question (0 until reviewed, then `min( 1, stability / days )`), averages a concept's questions, calls a concept uncovered (no enrolled note still in the vault is mapped to it), weak (mastery under 0.7) or solid, and rolls up a subject's `coverage` and `mastery` (uncovered concepts count 0, so mastery never exceeds coverage); `listConceptUsage` reads the rows in two queries per subject and the days are the user's `melete_mastery_days` setting (7–90, default 21). They are null until the syllabus is approved and has concepts. `GET /api/melete/subjects/:id/gaps` (`meleteGaps.service`) returns the sections with their roll-ups, each concept's bucket, mastery and note and question counts, and the `next_step` (`nextStep` in `mastery.ts`: cover the first uncovered concept, else review the weakest weak one, else none; a draft syllabus is a 409). `GET /api/melete/review/next?concept=` serves that concept's active questions (`listForConcept`): overdue first, then not yet due, then never asked, outside the day's new-question limit; a question already reviewed today and not due again is left for the next day, so a concept review ends after one pass. `POST /api/melete/concepts/:id/suggestions` (`meleteSuggest.service`, ADR 0093) asks Claude for 3–5 resources for one concept in a single synchronous call (60 s, no tools), strips every link from every field (`melete/suggest.ts`), records a `suggest` run and stores nothing; a failure is a 502 with a failed run. The web turns each query into a YouTube search (video, talk) or a web search. `GET /api/melete/today` gives every subject `coverage`, `mastery`, `syllabus_status`, `target_level`, `due_today` (due before the study day ends) and `seconds_this_week` (0 until time is recorded); the Today page shows one card per subject above **Review all due**.

Themis and time (v1.1, ADRs 0091, 0092): schema 16 adds `themis_areas`, `themis_goals` (one outcome type each: learning, metric or check-in, fixed at creation, with CHECKs tying the fields to the type), `themis_metric_updates`, `themis_checkins` (one per goal and period), `time_entries` (`measured` sessions of a subject or `logged` minutes of a subject or a goal, one target each) and `melete_subjects.goal_id`. `themis` joins `ModuleId`, so migration 16 rebuilds `user_modules` with the wider CHECK (the `eligible_users` view names it, so the view is dropped and recreated unchanged around the rebuild); members start without it and the admin has every module. An area is deleted only when it has no goals (`themis_goals.area_id` has no cascade); deleting a goal removes its updates, check-ins and logged time and unlinks its subjects. The routes (`/api/themis/*`, behind `requireModule( 'themis' )`, the same 404 as an unknown route for a user without it) are in `themis.routes.ts`, rules in `themis.service.ts`: areas and goals are created at the end of their list, `PATCH` with a `position` moves one and renumbers its siblings (a position past the end means the end), a goal moved to another area goes to the end of it, an area name is unique per user ignoring case (409), deleting an area that has any goal is a 409, the outcome can't be changed (the body is refused) and the unit, target and cadence apply only to goals of that outcome (400 otherwise), and a status change to `achieved` or `dropped` stamps `status_changed_at` (back to `active` clears it; an unchanged status keeps it). Area and goal names are user content and never logged (ADR 0049). Periods are pure functions in `themis/periods.ts` over study-day strings (`studyDay( now )` uses Melete's day start and `APP_TIME_ZONE`; weeks Monday–Sunday, calendar months and quarters; `checkinDue` is the period just finished, from the first day of the new one, for an active goal that existed in it and has no answer, so a missed period is a gap and not a backlog). `POST /api/themis/goals/:id/metric` records a value stamped now (409 for a goal that isn't a metric goal) and `POST /api/themis/goals/:id/checkins` records a 1–5 rating for the period currently due only (400 for any other period or a goal that isn't due, 409 for a second answer or a goal that isn't a check-in goal). Subjects link to a goal two ways: `PUT /api/themis/goals/:id/subjects { subject_ids }` sets exactly that list (it needs Melete as well as Themis, 404 without; a subject that isn't the caller's is a 404 and nothing changes; a subject moves over from the goal it had, since it belongs to at most one) and `PATCH /api/melete/subjects/:id { goal_id }` (an unknown or another user's goal is a 404, an achieved or dropped one a 400, `null` unlinks). `GET /api/themis/overview?period=week|month|quarter` (`themisOverview.service`) returns the period's study-day range, the check-ins due and the areas in order, each with its **active** goals as cards (achieved and dropped goals are left out but keep their history): a learning goal's outcome pools coverage and mastery over every concept of its linked approved subjects (`themis/overview.ts`, `pooledLearning`; concept-weighted, so it is not the mean of the subjects' own numbers; null with no approved subject), a metric goal's is its latest value, target, unit and last 8 updates, a check-in goal's its last 8 ratings. `GET /api/themis/goals/:id` adds the full update and check-in history, the linked subjects and twelve weeks of time. `GET /api/themis/goals` (ADR 0095) lists every goal of the user whatever its status, in area order, each with its area's name and nothing else, so the web's All goals list can reach the achieved and dropped goals the overview leaves out.

Measured time (v1.1, ADR 0091): each saved answer calls `recordAnswerTime( userId, subjectId, at )` (`time.service.ts`) inside `recordReview`'s transaction, so a review that is refused or rolled back leaves no time. `time/session.ts` (pure) extends the subject's latest `measured` session when the answer comes within `melete_session_gap_minutes` (default 5, 1–30) of its end, or starts one; a session runs from its first answer to its last plus `melete_final_card_seconds` (default 30, 0–120), is never under a second, and keeps the study day it started on. Grading an answer records nothing. `seconds_this_week` on a subject is the sum of its entries (measured and logged) whose study day falls in the current Monday–Sunday week (`sumSubjectSeconds`).

Logged time and period totals (v1.1, ADRs 0091, 0092): `/api/time-entries` (`timeEntries.routes.ts`, not behind a module: a user's time is their own, and each target is checked instead) takes `POST { subject_id | goal_id, day, minutes, note? }` (a subject needs the caller's Melete and a goal their Themis, both their own, else the 404 of an unknown id; `minutes` 1–1440; `day` a study day no later than today and no more than 365 days back), `PATCH` (minutes, day or note; a `calendar` entry's target can also change, a logged one's never) and `DELETE` for `logged` and `calendar` entries (a measured one is a 409), and `GET ?from&to` (both required, newest day first). Period totals come from `timeByGoal`, one grouped query: a goal's time is what was logged against it plus every entry on the subjects linked to it now (so relinking moves a subject's past time), split into `measured`, `logged` and `calendar`; an area's is the sum of its active goals' cards, so achieved and dropped goals and subjects linked to no goal are not in it. A goal's detail gives twelve weeks of measured, logged and calendar seconds, oldest first; `seconds` is always the sum of the three.

Calendar time (v1.2, ADR 0108): a user with Themis can connect one Google Calendar read-only from Settings › Sources (`/api/calendar/*`, behind `requireModule( 'themis' )`; the same OAuth client as Gmail with its own redirect `CALENDAR_REDIRECT_URI`, the refresh token encrypted with the same key; `google/` holds the token cipher and the OAuth state store that Gmail and Calendar share, `calendar/` the OAuth and the only Calendar API client). There is no poller: `POST /api/calendar/sync` (Sync now, or when Home opens, skipped by `?if_older_than=`) reads the window from `max( import_from, now − CALENDAR_LOOKBACK_DAYS )` to now with recurring events expanded, and only after a complete read reconciles `calendar_events` in one transaction (`calendar/reconcile.ts`, pure): finished timed events become **drafts**, drafts follow their event or go when it does, approved and dismissed rows stay as markers so nothing is imported twice. Only the title and times are stored, and no title is logged. Title rules (`calendar/rules.ts`, pure: a phrase contained in the title, case-insensitive, first by position) pre-assign drafts to a subject or a goal; a change to the rules reapplies them to drafts that are unassigned or rule-assigned and leaves hand assignments alone. Approving a draft (one, or all rule-matched) subtracts the seconds that measured Melete time already covers inside the event (`calendar/overlap.ts`, the union of the measured intervals of the subject, or of every subject linked to the goal), stores the rest as a `calendar` time entry owned by Atlas and records nothing when measured time covers it all. `calendar_account`, `calendar_rules` and `calendar_events` came with schema 19, which also rebuilt `time_entries` to accept the `calendar` source. `GET /api/themis/overview` carries `calendar_drafts` and `calendar_status`, and Status shows a Calendar connection row once an account exists. The e2e stack has no consent screen: its fakes server answers `events.list`, `calendarList` and the token refresh (`CALENDAR_API_BASE_URL`, which also moves the OAuth token endpoint, test-only), and `home-calendar.spec.ts` seeds a connected account into the stack's database.

Web layout (ADR 0098): `apps/web/src` is grouped by feature, not by kind. `features/<feature>/` (jobs, feeds, inbox, gmail, vault, settings, status, admin, melete, themis) holds its screens, hooks, api calls and fixtures; `app/` holds the shell, the gate and the signed-in user; `lib/` holds `request`, `apiError`, `queryKeys` and the formatters and imports no feature; the `src/` root has only the five wiring files and their tests. A feature that needs another's data imports it by path; nothing re-exports at feature level.

The web gate (ADRs 0068, 0070, 0063): `AuthGate` is the root route element, reads `useMe`, and is the one place that decides what a user sees; pages never check auth. It shows exactly one of, in this order: loading; an error from `useMe`; the sign-in page when there is no session (`me` is `null`; a 401 is not an error to `getMe`); the vault page (`ChooseVault`) when the user has no vault or the server reports `vault_missing` (the old folder is named in a warning); a "no modules" page when the admin has switched none on; otherwise the app. The first four render on a bare `GatePage` without the shell. A 401 from any query or mutation, and the 409 whose message is `VAULT_MISSING_MESSAGE`, invalidate the `me` query, so the gate re-decides without a reload. `ChooseVault` offers the unclaimed folders and, only while the server's `can_create` is true (false on the VM, ADR 0075), a New vault form; otherwise it tells the person to ask the admin to set up the sync. `RequireModule` sends a user without a route's module to `homeFor( modules )` in `moduleHome.ts`, as does `HomeRedirect` for an unknown path. Sign-in is a full-page trip to `/api/auth/google?returnTo=<current path>`. `Me` also carries `study_today`, the server's study day (`APP_TIME_ZONE`, `MELETE_DAY_START_HOUR`); the Log time dialog takes its default day and its latest day from it and never reads the device's date.

Melete and Themis in the web app (v1.1, ADRs 0089–0095): a user who has Themis lands on Home at `/` (ADR 0109), first in the drawer, then Themis, the transcriber and Melete (`moduleHome.ts` holds the order; Home is not a module and shows only with Themis), and the transcriber lives at `/transcriber` and `/transcriber/jobs/:id` (`/jobs/:id` redirects); Settings › Sources has a Google Calendar section beside Gmail for users with Themis (connect through Google and back to `/settings/sources?calendar=…`, choose a calendar and the import start day, sync now, change calendar, disconnect with an option to remove imported time); `/themis/calendar` (Themis only) has two tabs, Drafts (each event with its day and time, what counts after measured time is subtracted, a subject or goal picker, a note, Approve, Dismiss and Make a rule, plus Sync now and Approve all matched) and Rules (title phrases in order with up, down and delete, and an add row); the Themis page links to it; Home shows the time by area (measured, logged and calendar as three shades), the top five goals and the calendar cards (drafts waiting, or an invitation to connect), and reads the calendar when it opens; the Themis page at `/themis` shows the check-ins due (answered in place), where the time went for the week, month or quarter (measured and logged as two shades, no chart library) and the goals by area with their outcome. A goal's page (`/themis/goals/:goalId`) has its history, time by week, linked subjects and the edit, metric update, link and delete actions; **All goals** is `/themis?view=all`, fed by `GET /api/themis/goals` (ADR 0095). **Log time** is one shared dialog, opened from a floating button on the Themis home and from a Melete subject. Melete's landing is a card per subject (coverage and mastery, due today, time this week) above **Review all due**; a subject is four tabs (Overview with the gap view, Syllabus, Notes, Settings, where its goal is chosen). The web holds no rule of its own: coverage, mastery, periods and time all come from the server.

## Accounts and multi-user

Accounts (ADRs 0061–0069): everything above is per person. Each person signs in with Google (the server runs the OAuth code flow with PKCE; the first account must be `ADMIN_EMAIL`, after that only users the admin has added), gets a server-side session (a cookie holding a random token, only its hash stored, sliding expiry), and sees only the modules the admin has switched on (Transcriber, Melete, Themis; `requireModule` answers 404). Every table has a `user_id`; repositories take `userId` first and a query without it is a bug (a guard test enforces this), except `system.repository.ts` (the loops, across users) and the `users`, `sessions` and `app_settings` repositories; another user's resource is a 404, never a 403. Each user has a vault, a folder directly under `VAULTS_PATH`, claimed or created on first sign-in (`vaultRootFor( userId )`), which the agent receives as `vault_dir` and resolves under its read-only `VAULTS_ROOT`. The worker, the intake poller and the Melete generator serve every user with work waiting, taking turns (the `eligible_users` view: module on, vault chosen, not removed). The admin adds, removes, restores and deletes users, resets vaults (the folder is moved to `.released/` under `VAULTS_PATH`, which no one can claim, ADR 0097) and reads a usage rollup in Settings → Admin (`/api/admin`, `requireAdmin`); prompt profiles, models and settings are per user, while the feed interval and the agent, transcription and replication status are app-wide and admin-only (a user's vault-sync row is visible to that user and to the admin). The 0.9 database is a fresh baseline: an older database is copied to `pre-migration/` next to the database as `pre-0.9-<stamp>.db` and set aside (ADR 0066). The e2e stack signs in through a test-only session route that the server refuses to start with outside `NODE_ENV=test`.

Turns between users (ADRs 0062, 0064): the worker, the intake poller and the Melete generator serve everyone through `system.repository.ts`, the one place with queries that have no user. `claimNextJob` and `claimNextGeneration` consider only eligible users (active, with the module on, the admin always, and for Melete a chosen vault): `eligible_users` lists active members once per module they have, and `eligible()` adds the admin once per `ModuleId`, and the user whose `last_job_started_at` or `last_generation_started_at` is oldest goes next: users who have never started come first, then the one who joined first. The claim stamps the user in the same transaction, so a busy user cannot starve another. `claimNextJob` does not move the job, because the source adapter makes the first move. A user whose module is off, or who was removed, keeps their queued work untouched until access returns; `listDueFeeds` and `listDueGmailSources` also skip them, while `listExpiredJobs` ignores eligibility so expiry still runs for everyone.

Modules (ADR 0101): `ModuleId` in `@atlas/shared` is the only place a module is named. `user_modules.module` has no `CHECK` and the view names no module, so adding a module is one `ModuleId` entry plus its routes in `MODULE_ROUTES` (`app.ts`), which mounts `requireModule` for every module; the application validates names (`setModules` refuses an unknown one, `listModules` ignores a stored one it no longer knows).

Waking the loops (ADR 0100): the worker and the Melete generator run a pass when a service queues work (`worker/wake.ts`, a small emitter whose wake is delivered in a microtask) and every 15 seconds as a safety net. A wake during a pass is ignored: the pass keeps claiming until nothing is left, and the poll covers the instant between its last empty claim and its end. A path that does not wake costs at most 15 seconds, never a lost job.

Origins behind a proxy (ADR 0071): `requestOrigin( req, origins )` and `requestScheme` (`middleware/requestOrigin.ts`) believe `X-Forwarded-Host` and `X-Forwarded-Proto` only from a loopback or private-network peer (127.0.0.1, `::1`, 10/8, 172.16/12, 192.168/16, fc00::/7). Docker Desktop shows a request that came in through the published port, Tailscale Serve's included, as coming from its gateway (192.168.65.1 observed), so loopback alone would never match; Compose publishes the port on 127.0.0.1 only, so nothing else on a private network reaches the server directly. From any other peer the headers are ignored. Whatever the source, the answer is always one of `APP_ORIGINS`, else `UnknownOriginError` (400). When a trusted peer sends no forwarded host, both the request's own scheme and `https` are tried, because Tailscale Serve may pass `Host` through unchanged. The same peer test guards `GET /api/health` (`requireTrustedPeer`): a peer outside loopback and the private networks gets the standard 404, while `deploy.sh`, the Compose healthcheck and e2e all connect locally.

## Hosting on the VM

On the VM, `compose.prod.yml` adds a one-shot `restore` service (Litestream, only if there is no database and a replica exists), a `litestream` sidecar, and one `sync-<user>` Obsidian Headless container per synced user that writes a status file the app reads (ADR 0075); secrets come from Secret Manager into `/run/atlas/secrets.env` when the `atlas` systemd unit starts (ADR 0078), and `VAULT_CREATE_ENABLED=false`. The app port is published on `127.0.0.1` only; phone access is Tailscale Serve (documented in `docs/phone-access.md`, not coded), with a web app manifest and no service worker (ADR 0060).
