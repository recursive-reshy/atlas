# Architecture

How Atlas works today, one section per area. The reasons behind each part are in `docs/decisions/` (the ADR numbers below). Read this file before changing how a part works, and update it in the same commit when you do. Each app's `CLAUDE.md` holds its own language, style and local rules.

## Request flow and source adapters

The web app submits a URL to `POST /api/jobs`; the URL is a video (YouTube only; other video sites are refused with "Only YouTube videos are supported") or an article, detected from the host and overridable. The server queues a job and its worker runs it in the background, one at a time, through a source adapter that turns the job into one source document (ADR 0030).

## Transcription

For a video, the YouTube Data API gives the title, channel and length (`YOUTUBE_API_KEY`), then the Gemini Developer API (`GEMINI_MODEL`, `GEMINI_API_KEY` as a header, plain `fetch`; Vertex AI refused YouTube input from the VM's service account) is given the public YouTube link and writes the transcript in one request, so nothing is downloaded and the VM never contacts YouTube for the video (ADRs 0081–0083); if Gemini stops at its output limit the partial transcript is kept and marked truncated; the transcript is stored as metadata plus plain text, with no timestamps (ADR 0074), and formatters render it as Markdown (default) or TXT.

## Articles, feeds and Gmail

For an article, the server fetches the page itself, extracts the main text with Readability and stores it as Markdown (ADR 0031); a page it can't read is handled by pasting the article's text, which skips the fetch. Gmail (ADR 0035): Naresh connects his account once in Settings (read-only OAuth run by the server, the refresh token stored encrypted with a key from `.env`), adds sources that match emails by Gmail labels or a search, and the same poller reads new matching emails; each waits in the same inbox, and summarizing one converts the email's whole body to Markdown (ADRs 0036, 0040) and queues an article job whose note links back to the email, so nothing downstream knows it came from Gmail (one inbox for feed items and emails, ADR 0038; job-alert intake is deferred, ADR 0041). Feeds (ADR 0032): Naresh subscribes to RSS or Atom feeds in Settings, a poller in the server process checks them on a schedule, and new items wait in the inbox on the home page; nothing is fetched or summarized until he summarizes an item (or switches a feed to summarize automatically), which turns it into a normal job.

## Summaries and prompt profiles

The worker then sends the transcript or article to Claude for a summary (title, key points, quotes, tags; article notes have no timestamps). What the summary focuses on comes from a prompt profile, a named, versioned and editable guidance text that Naresh manages in Settings (the locked instructions that keep the output shape are always sent with it), and the model is chosen in Settings and can be overridden per video; both can be changed and the summary regenerated from the review screen. Every summary attempt is recorded with its model, prompt version, tokens and estimated cost.

## Linking and the agent

Linking (ADRs 0042–0046): when a summary completes and `AGENT_SECRET` is set, the job enters a `linking` status and the worker calls the vault agent service (`apps/agent`, reached at `AGENT_URL` with a bearer secret) with the note; the agent runs a Claude tool-use loop over read-only vault tools and returns link suggestions (existing notes, existing concepts or new concepts, each with an anchor phrase or a place under `## Related`), which the server stores per job with its own run record (model, linker prompt version, tool calls, tokens, cost). Linking never fails a job: on any error the job goes to review with a link error and can be retried. The linker prompt is a second, editable profile in Settings, with locked instructions served by the agent.

## Review and save

In review Naresh accepts or rejects each suggestion; accepting inserts the `[[wikilink]]` into the stored draft in one transaction with the decision, so the vault is still written only by the save. The note is stored as one Markdown string, front-matter included. Naresh reviews and edits it in the web app, which autosaves it to the server as a draft (each save restarts the 24-hour expiry), and chooses a vault folder for it; saving writes the stored draft into that folder of the Obsidian vault (a mounted folder, all writes confined to it) and deletes the transcript. Jobs are stored in SQLite, and unreviewed ones expire after 24 hours without an edit. The web app polls the job's status and offers the downloads.

## Lifecycle, logs and Status

Lifecycle (ADR 0048): every job status and allowed move is defined once in `apps/server/src/jobs/lifecycle.ts`; `moveTo` enforces it, sets expiry from the target state and logs a refused move, and the repository's status lists come from it. Logs (ADR 0049): the server (pino) and the agent write one JSON object per line, a job's ID is on every line about it and travels to the agent as `X-Job-Id`, and no secrets or note text are logged. Status (ADR 0050): every check of a feed, Gmail source, the Gmail connection, the agent, the transcription model, replication (when `LITESTREAM_METRICS_URL` is set), and each user's vault sync (when `VAULT_SYNC_STATUS_DIR` is set) goes through one `recordCheck` into `health_status` (the last 5 errors in `health_errors`); `GET /api/status` feeds the Status panel on the Settings → Sources tab and the warning badge on the drawer's Settings item.

## Backups and replication

Backups (ADR 0076, which supersedes 0051): the manual button is gone; on the VM Litestream replicates the database to a bucket, and the server only sets `busy_timeout = 5000`, writes its pre-migration and pre-0.9 set-aside copies to `pre-migration/` next to the database, and refuses to start on a database from a newer version.

## Settings

Settings (ADR 0052) is routed tabs, Prompts / Models / Sources, under a data router with one unsaved-changes guard.

## Melete

Melete (ADRs 0054–0060) is a second module of the same server, web app and database: the user picks a learning root in the vault, each folder in it is a subject, and a scan (on demand, 30-second rule, no watcher) tracks notes by path and a body hash so moves keep their history (ADR 0057); a folder or note it can't read is skipped, its notes are left exactly as they were, and the Melete page lists the skipped paths until a later scan reads them. The folder picker skips an unreadable folder the same way and logs it. Enrolled notes are queued in `melete_notes` and a generator loop beside the worker asks Claude for recall questions in one call from Express, not the agent (ADRs 0055, 0058); questions are scheduled with FSRS through `ts-fsrs` at 90% target recall (ADR 0056). In review, typed answers are graded by a second Claude call that suggests a rating, or the user rates in quick mode; the rating updates the card and writes a review row in one transaction. **Melete never writes to the vault** (the one exception is the empty learning-root folder a user creates from Settings, made on save, ADR 0072); it reads it and keeps all its data in the `melete_*` tables, and its two prompts are profiles in Settings with a `purpose`. The seeded Study summary profile and folder memory (the picker starts on the last folder used with the job's profile, `Job.default_folder`) are ADR 0059.

Concept layer (v1.1, ADRs 0089, 0094): schema 15 gives a subject a target level, an intent and a syllabus status, and adds sections, concepts, note-to-concept mappings and a concept label on each question. The syllabus is drafted by Claude (`draftSyllabus`, one call from the subject's name, target level, intent and the titles and openings of its notes, `melete/syllabus.ts` trims it to at most 80 unique concepts): `POST /api/melete/subjects/:id/syllabus/draft` only sets the subject `drafting`, and the Melete generator loop, which takes drafts before question generation, makes the call and stores it as `draft` or `failed` (the old syllabus is kept on a failure, and a subject left `drafting` by a restart is simply taken again). Each attempt is a `syllabus` row in `melete_runs`. The draft is edited as a whole: `PUT .../syllabus` is diffed against the stored one by id (`melete/syllabusDiff.ts`), so a renamed or moved concept keeps its mappings and question labels and only a removed one loses them; `POST .../syllabus/approve` sets `approved` and queues every enrolled note for mapping. For an approved syllabus, question generation is one call that also maps the note (`generateApprovedQuestions`): Claude sees the concepts as short refs (`c1`…, `melete/conceptRefs.ts`) and answers with the note's concepts (at most 5), an off-syllabus suggestion when none fits, and a concept ref on each question; the server maps refs back to ids, gives a question outside the note's concepts the first one, stores the mapping as `claude` (hand pins are cleared, since the content changed) and flags an unmapped note `off_syllabus`. An unapproved subject keeps the plain call. Syllabus-driven remaps use a separate **Map** call (`mapNote`, `melete/map.ts`, `services/meleteMapping.service.ts`): a note is queued with `mapping = 'queued'`, the Melete loop takes it third (after drafts and generation, and only once its questions are not waiting) and claims it with `claimNextMapping`, which takes the same turns between users. Map rewrites the note's mapping and its questions' concept labels and nothing else, so no card, state or question changes; a hand-mapped (pinned) note keeps its concepts and is only labelled (a pin with no concepts left, after a redraft, is mapped in full and unpinned). A failure sets `mapping = 'failed'` with the reason, keeps the old mapping and is retried with `POST /api/melete/notes/:id/retry`; notes left `mapping` by a restart are requeued at start. Remaps are queued, never run inside a request: approving queues every enrolled note; a save of an approved syllabus queues the unpinned `flagged` notes when a concept was added and the unpinned notes left with no concept when one was removed (a rename, a new description or a move queues nothing); `POST .../syllabus/remap` queues every enrolled, unpinned note. A note Map is working on now is never queued again. A hand edit (`PUT /api/melete/notes/:id/concepts`) writes the mapping as `hand`, pins the note, clears its off-syllabus flag and queues a labels-only Map; `POST /api/melete/notes/:id/off-syllabus` either dismisses the flag or adds the suggested concept to a chosen section and maps the note to it by hand (and queues the other flagged notes, since a concept was added). The Notes tab shows each note's concepts, its mapping state and the flag; the note page has the mapping editor. Coverage and mastery (ADR 0090) are computed on every read, never stored: `melete/mastery.ts` (pure) scores each active question (0 until reviewed, then `min( 1, stability / days )`), averages a concept's questions, calls a concept uncovered (no enrolled note still in the vault is mapped to it), weak (mastery under 0.7) or solid, and rolls up a subject's `coverage` and `mastery` (uncovered concepts count 0, so mastery never exceeds coverage); `listConceptUsage` reads the rows in two queries per subject and the days are the user's `melete_mastery_days` setting (7–90, default 21). They are null until the syllabus is approved and has concepts. `GET /api/melete/subjects/:id/gaps` (`meleteGaps.service`) returns the sections with their roll-ups, each concept's bucket, mastery and note and question counts, and the `next_step` (`nextStep` in `mastery.ts`: cover the first uncovered concept, else review the weakest weak one, else none; a draft syllabus is a 409). `GET /api/melete/review/next?concept=` serves that concept's active questions (`listForConcept`): overdue first, then not yet due, then never asked, outside the day's new-question limit; a question already reviewed today and not due again is left for the next day, so a concept review ends after one pass. `POST /api/melete/concepts/:id/suggestions` (`meleteSuggest.service`, ADR 0093) asks Claude for 3–5 resources for one concept in a single synchronous call (60 s, no tools), strips every link from every field (`melete/suggest.ts`), records a `suggest` run and stores nothing; a failure is a 502 with a failed run. The web turns each query into a YouTube search (video, talk) or a web search. `GET /api/melete/today` gives every subject `coverage`, `mastery`, `syllabus_status`, `target_level`, `due_today` (due before the study day ends) and `seconds_this_week` (0 until time is recorded); the Today page shows one card per subject above **Review all due**.

Themis and time (v1.1, ADRs 0091, 0092): schema 16 adds `themis_areas`, `themis_goals` (one outcome type each: learning, metric or check-in, fixed at creation, with CHECKs tying the fields to the type), `themis_metric_updates`, `themis_checkins` (one per goal and period), `time_entries` (`measured` sessions of a subject or `logged` minutes of a subject or a goal, one target each) and `melete_subjects.goal_id`. `themis` joins `ModuleId`, so migration 16 rebuilds `user_modules` with the wider CHECK (the `eligible_users` view names it, so the view is dropped and recreated unchanged around the rebuild); members start without it and the admin has every module. An area is deleted only when it has no goals (`themis_goals.area_id` has no cascade); deleting a goal removes its updates, check-ins and logged time and unlinks its subjects. The routes (`/api/themis/*`, behind `requireModule( 'themis' )`, the same 404 as an unknown route for a user without it) are in `themis.routes.ts`, rules in `themis.service.ts`: areas and goals are created at the end of their list, `PATCH` with a `position` moves one and renumbers its siblings (a position past the end means the end), a goal moved to another area goes to the end of it, an area name is unique per user ignoring case (409), deleting an area that has any goal is a 409, the outcome can't be changed (the body is refused) and the unit, target and cadence apply only to goals of that outcome (400 otherwise), and a status change to `achieved` or `dropped` stamps `status_changed_at` (back to `active` clears it; an unchanged status keeps it). Area and goal names are user content and never logged (ADR 0049).

## Accounts and multi-user

Accounts (ADRs 0061–0069): everything above is per person. Each person signs in with Google (the server runs the OAuth code flow with PKCE; the first account must be `ADMIN_EMAIL`, after that only users the admin has added), gets a server-side session (a cookie holding a random token, only its hash stored, sliding expiry), and sees only the modules the admin has switched on (Transcriber, Melete; `requireModule` answers 404). Every table has a `user_id`; repositories take `userId` first and a query without it is a bug (a guard test enforces this), except `system.repository.ts` (the loops, across users) and the `users`, `sessions` and `app_settings` repositories; another user's resource is a 404, never a 403. Each user has a vault, a folder directly under `VAULTS_PATH`, claimed or created on first sign-in (`vaultRootFor( userId )`), which the agent receives as `vault_dir` and resolves under its read-only `VAULTS_ROOT`. The worker, the intake poller and the Melete generator serve every user with work waiting, taking turns (the `eligible_users` view: module on, vault chosen, not removed). The admin adds, removes, restores and deletes users, resets vaults and reads a usage rollup in Settings → Admin (`/api/admin`, `requireAdmin`); prompt profiles, models and settings are per user, while the feed interval and the agent, transcription and replication status are app-wide and admin-only (a user's vault-sync row is visible to that user and to the admin). The 0.9 database is a fresh baseline: an older database is copied to `pre-migration/` next to the database as `pre-0.9-<stamp>.db` and set aside (ADR 0066). The e2e stack signs in through a test-only session route that the server refuses to start with outside `NODE_ENV=test`.

## Hosting on the VM

On the VM, `compose.prod.yml` adds a one-shot `restore` service (Litestream, only if there is no database and a replica exists), a `litestream` sidecar, and one `sync-<user>` Obsidian Headless container per synced user that writes a status file the app reads (ADR 0075); secrets come from Secret Manager into `/run/atlas/secrets.env` when the `atlas` systemd unit starts (ADR 0078), and `VAULT_CREATE_ENABLED=false`. The app port is published on `127.0.0.1` only; phone access is Tailscale Serve (documented in `docs/phone-access.md`, not coded), with a web app manifest and no service worker (ADR 0060).
