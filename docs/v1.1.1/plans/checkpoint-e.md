## 5.1 Modules defined once (ADR 0101 first)

**What is true today.** `ModuleId = z.enum([transcriber, melete, themis])` in `packages/shared/src/auth.ts` is already the registry for validation. `user_modules` has `CHECK ( module IN ( 'transcriber', 'melete', 'themis' ) )` (migration 16, `sql/16-themis-and-time.sql`). The view `eligible_users` is `users JOIN ( SELECT 'transcriber' UNION ALL SELECT 'melete' ) m` with the admin rule, used only by `eligible()` in `repositories/system.repository.ts` (6 call sites: job claim, due feeds, due Gmail sources, note generation, mapping, drafts). `app.ts` has three `requireModule` lines.

**Migration 17** — `sql/17-modules-registry.sql`, entry `'17-modules-registry'` appended to `migrationFiles` in `repositories/database.ts` (ADR 0099 layout):
- `DROP VIEW eligible_users`; rebuild `user_modules` without the `CHECK` (same pattern as migration 16: `_new` table, `INSERT … SELECT`, drop, rename; same PK and `ON DELETE CASCADE`); recreate `eligible_users` as **members only**: `users u JOIN user_modules um ON um.user_id = u.id WHERE u.status = 'active'`, columns `user_id, module, vault_dir` unchanged. No module is named in it.
- The admin rule moves to the query: `eligible()` in `system.repository.ts` joins a derived table `eligible` = `eligible_users UNION ALL ( SELECT u.id, j.value, u.vault_dir FROM users u, json_each( '<ModuleId.options as JSON>' ) j WHERE u.role = 'admin' AND u.status = 'active' )`. `eligible()`'s `module` argument becomes `ModuleId`. The three `eligible_users.vault_dir IS NOT NULL` conditions become `eligible.vault_dir`. **Deviation from TRD wording, recorded in ADR 0101:** TRD 6.1 says the list is "passed as a parameter"; the six queries mix positional parameters in a fixed order, so the list goes in as a SQL literal built once from `ModuleId.options` (a code constant, never user input — the module name is already inlined into these queries today). Behaviour is the same: the admin is eligible for every module the application knows, the SQL names none.
- Row counts unchanged, so `ALLOWED_COUNT_CHANGES` stays empty.

**Tests first (red → green):**
1. `fixtures/schema-17.sql` (the seed a locked 17 requires: `fixtures.guard.test.ts` demands one per locked version; the data is the schema-16 seed, tables are unchanged) — written first; the guard fails until the migration exists and is locked.
2. `database.upgrade.test.ts`, new cases for 17 (`openSeeded( 16 )` then run all migrations): both users' modules kept in order; an unknown module value (`'metis'`) is now accepted by SQL (the 16 test that expects `CHECK` to throw runs against `migrations.slice( 0, 7 )` and is untouched); `eligible_users` lists members' active rows only; FK `ON DELETE CASCADE` still removes a deleted user's rows; `foreign_key_check` empty. The generic "row counts unchanged" test covers the rebuild.
3. `database.test.ts` "lists a user once per module in eligible_users, and the admin for every module" (line ~744) asserts the old view. **TRD-sanctioned change** (the view no longer lists the admin): it becomes "lists an active member once per module they have", and the admin half moves to a new `system.repository` test (see 4). Named in the log line.
4. `repositories/system.repository.test.ts`: for each `ModuleId` that a loop uses (`transcriber`, `melete`), the admin is served with no `user_modules` row; a member only with the module on; a removed member not; a module the application does not know (a stray `user_modules` row `'metis'`) serves nothing. Red first: after the view change but before `eligible()` changes the admin test fails for the right reason.
5. `userModules.repository.ts` `listModules` currently `ModuleId.parse`s every row, so a stray or retired module name in the now-unconstrained table would make `GET /api/me` throw. Test first: `listModules` ignores rows that are not a known `ModuleId`; then `safeParse`/filter. (Application code is now the only validator, as the task says.)
6. `app.ts`: `MODULE_ROUTES: Record< ModuleId, string[] >` exported from `app.ts` and mounted in one loop (`transcriber`: jobs, feeds, inbox, gmail, vault; `melete`: `/api/melete`; `themis`: `/api/themis`; same paths as today). Test (`app.test.ts` or beside the existing requireModule route tests): for every `ModuleId` and every path in `MODULE_ROUTES`, a member without that module gets 404 `{ error: 'Not Found' }` and the admin does not; `Object.keys( MODULE_ROUTES )` equals `ModuleId.options`. `Record< ModuleId, … >` makes a new `ModuleId` without routes a compile error.

## Open points (my defaults unless you say otherwise)
1. **Admin rows in the view.** TRD 6.1 allows the view to be "user_modules plus the admin rule"; a view cannot take the module list, so the admin branch lives in `eligible()` with the list as a literal from `ModuleId.options`. The alternative (positional parameter in all six queries) is more error-prone for no gain.
2. **`listModules` ignores unknown rows** rather than throwing, now that SQL no longer rejects them. Not in the TRD but a direct consequence of dropping the `CHECK`; covered by a test.
